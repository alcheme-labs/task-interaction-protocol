# Integrate Task Interaction Protocol

Work in the consuming application and answer in the user's language. Locate the matching protocol checkout. In the distributed layout the repository root is two directories above this Skill's **real directory** (resolve any symlink first). If the Skill was copied alone, use the matching checkout in the workspace or obtain it from the official repository. The definition schema, message schema and worked cases there describe one version. [Protocol repository](https://github.com/alcheme-labs/task-interaction-protocol) · [Protocol overview](../../README.md) · [Chinese edition of this Skill](SKILL.zh-CN.md)

## Find the owner of one real handoff

Trace one task from the user's entry point to the person or agent who reads the accepted deliverable. Identify the actual assignment, authorization context, task service, durable result and read interface. Choose the part the user asked to build.

- **Calling an existing service.** Discover the authorized version, capabilities and catalog with `describeTaskProtocol`. Map the application's transport or agent tools to the existing service. Read its receipts and views. The service owns progress.
- **Implementing the task service.** Find the current definition publisher, assignment store, transaction boundary, content owner and trusted source adapters. Extend the existing owners. The kernel alone installs successors. The host chooses its transport and storage. Section 6 illustrates one host's mapping. [Storage and adoption](../../docs/protocol-and-runtime-boundaries.md#storage)

## Connect the operations

1. Turn each independently submitted result or decision into an activity with one role and one goal. Map explicit inputs, outputs, checks and exits. Use `distinctRoles` when the request requires different people. Resolve canonical principals behind aliases at launch. Use a check for a candidate verdict, a wait for a fact from a bound source, and `after` for a notification. Validate the document and the actual capabilities of the intended host. A missing capability should identify the affected path and preserve the requirement. [Definition schema](../../definition.schema.json) · [Runnable example](../../examples/en/review.task.json)
2. Separate registration from dispatch. After `validateDefinition`, an authorized `publishDefinition` uses the expected base revision and a stable request ID. With `readDefinition` read the exact reference in the receipt and compare the complete document. If only registration was requested, finish there. Launch requires a requested and authorized assignment, its pinned revision, role bindings and inputs. Read the first `getWork` as the bound assignee. Bind trusted source identity from host configuration and authentication. [Launch and binding](../../docs/protocol-and-runtime-boundaries.md#activation)
3. Use the published message envelopes (`protocolVersion`, `op` and one of `params`, `result` or `error`). Submit the current `workId`, `round`, `expectedViewSeq`, `requestId` and declared output through `submitResult`. Derive caller identity from authenticated context. Honor `allowedActions`, optional inputs and the material versions this caller can actually read. Treat returned `pending` as durable responsibility to finish the original attempt. A rejection permits correction in the same round. A return opens a new one anchored to the specified result and edit scope. [Message schema](../../messages.schema.json) · [Work and materials](../../docs/protocol-and-runtime-boundaries.md#work-view)
4. At the service boundary, `accept` commits the accepted result, transition, one successor and receipt atomically. A matching `signal` lets `resume` consume one particular wait and install one successor under the same guarantee. Verify source, subject, correlation and version or cursor as the wait requires. Only expose the source's own receipt. After an uncertain response, look up or replay the original key **with the original payload** under current permissions. For an external write with unknown outcome, use the provider's original request ID to reconcile it. Final readback identifies both the deliverable (`finalResultId`) and its closing decision (`decisionResultId`). [Transactions](../../docs/protocol-and-runtime-boundaries.md#transitions) · [Waits and recovery](../../docs/protocol-and-runtime-boundaries.md#external)

## Verify the integration

For a registration-only request, stop after exact definition readback under the granted permission. When testing execution or comparing interpreters, use the optional local walkthrough to validate and register `examples/en/review.task.json` in a temporary SQLite registry. In a new process, read the revision from the publication receipt. Pass the retrieved document to `replay.py` and `replay.mjs` with the matching `examples/en/conformance.json`. Both should reproduce all three cases' positions, outcomes and final content. `author.py describe` lists the local exercise's supported profile. Actor and source fields in the vectors are test inputs. [Runnable commands](../../README.md#local-walkthrough) · [Conformance vectors](../../examples/en/conformance.json)

Verify each requested behavior through the consuming system. For a review queue, read the first work as the writer, submit, read the new work as the reviewer, return it with a reason, revise and approve. Restart the host and read the selected revision and closing decision as an authorized reader. For registration-only work, verify exact definition readback after restart and zero dispatch. Exercise the applicable failure cases, including replay after a lost response, changed content under the same key, revoked access, and concurrent submissions or signals that must yield one handoff. Report which path actually ran and the result read from its owner. [Host acceptance cases](../../docs/protocol-and-runtime-boundaries.md#tests)

## Optional companion protocols

- For a **standalone server**, ServiceSeed (formerly ServerAgent) specifies how agents create, connect and maintain services within a service contract and explicit permissions. [ServiceSeed](https://github.com/alcheme-labs/ServiceSeed)
- To **connect a user-owned agent**, Agent Bridge Spec (`local-agent-bridge`) covers the application–agent connection and its authorization. Route task actions through the task service so it owns acceptance, transitions and receipts. [Agent Bridge Spec](https://github.com/alcheme-labs/agent-bridge-spec)
